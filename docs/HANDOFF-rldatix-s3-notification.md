# Handoff — RLDatix RL6 Release Notification (S3 source)

**Date:** 2026-08-04
**Status:** Framework in place; production notification generation not yet implemented.
**Branch:** `feat/notify-rldatix` (commit `5d61569`) on GitHub.

---

## Goal

Use the `RLDATIX_COMPARE_URL` from `.env` to detect the latest RL6 release
on the public RLDatix S3 bucket, and generate a **compact, well-formed HTML
notification** with links. This is for a user-facing "a new release was
published" alert — **not** a full change log. No detail beyond title,
date, version, and a link to the source.

## What the user explicitly does NOT want

- Anything based on `rldatix-public.zendesk.com` (Zendesk). The earlier
  work in this session explored that source, but the user has corrected
  the direction: **use the S3 URL**.
- A full per-fix enumeration. The HTML should be short — title, version,
  date, link, maybe one-line summary.
- Anything that requires authentication. The S3 bucket is public.

## The Source

`.env`:
```
RLDATIX_COMPARE_URL=https://elasticbeanstalk-us-east-1-420057813367.s3.amazonaws.com/Release_Notes/RL6/RL6_releasenotes.html
```

### Landing page (HTML, public)
The landing page is a static HTML page that **loads its data via AJAX
from two XML files**. The HTML body has empty `<table>` elements that
are populated client-side. Do not parse the HTML for release entries —
parse the XML files directly.

### The two canonical data feeds

| Feed | URL |
|---|---|
| Enhancements | `https://elasticbeanstalk-us-east-1-420057813367.s3.amazonaws.com/Release_Notes/RL6/release_notes_files/xml/Enhancements%20and%20Changes.xml` |
| Fixes | `https://elasticbeanstalk-us-east-1-420057813367.s3.amazonaws.com/Release_Notes/RL6/release_notes_files/xml/Fixes.xml` |

Both are public S3 objects, no auth, no rate limit observed. They are
well-formed XML with `<ROWSET><ROW></ROW</ROWSET>` structure.

### Per-row schema (both files)

| XML element | Meaning |
|---|---|
| `SummaryTitle` | Short headline for the change |
| `Summary` | Full prose description (HTML allowed inside; not always escaped) |
| `Product` | Comma-separated list of RL6 modules (e.g. `Risk, Feedback, Claims, Root Cause, Peer Review, Risk Register, Safety Huddles`) |
| `RLRefNumber` | Internal RLDatix reference number (e.g. `348717`). Often blank. |
| `Functionality` | Functional area (e.g. `Admin - Form Management`, `HL7 & Lookups`, `File Actions`) |
| `ReleaseNumber` | RL6 version string (e.g. `6.34`, `6.33.1`, `6.32`) |

### What's "latest"?

The version string is the highest-sortable token. As of 2026-08-04:

| Version | First observed |
|---|---|
| `6.34` | Most recent (current) |
| `6.33.1` | Hotfix |
| `6.33`, `6.32`, … `6.10` | Older majors |

Hotfix naming pattern: `<major>.<minor>.<patch>` (e.g. `6.33.1`).

Counts in the source as of 2026-08-04:
- **6.34:** 5 enhancements, 49 fixes
- **6.33.1:** 0 enhancements, 9 fixes (all 6.33 regressions)

### Footer / version signal
The landing HTML page footer reads `© 2026 RLDatix. All rights reserved.`
The `RL6_release_notes_cumulative.xlsx` file is also published at the
same path root:
- `release_notes_files/RL6_release_notes_cumulative.xlsx`

For notification purposes, the two XML feeds are sufficient.

## The Notification Output

User asked for a "well-formed and structured HTML links and information
related to the change, nothing detailed". Recommended shape:

```html
<h2>RL6 <VERSION> released</h2>
<p>
  <strong>RL6 <VERSION</strong> &mdash;
  <N enhancements>, <M fixes> &mdash;
  published <DATE if known>.
</p>
<p>Affected modules: <comma-separated list</p>
<ul>
  <li><a href="<sourceUrl>">Full release notes (RLDatix</a</li>
  <li><a href="<cumulativeXlsxUrl>">Download cumulative .xlsx</a</li>
</ul>
<p><em>Auto-generated by platform-automation VendorMonitor</em</p>
```

Notes on the design:
- One heading, no per-fix enumeration.
- Surface the totals (N enhancements / M fixes) and module list.
- Two outbound links: the landing page and the cumulative .xlsx.
- A footer line identifying the generator (provenance).
- For hotfixes (`X.Y.Z`), say "hotfix" instead of "released".

## Existing Framework (do not reinvent)

The repo has a vendor-monitor framework you can build on:

| Path | Use |
|---|---|
| `azure-pipelines/vendor-monitor.yml` | Schedule + state commit/push pipeline |
| `tasks/VendorMonitor/Run.ps1` | Entry point. Accepts `-Vendor`, `-ForceRecheck`, `-TestMode` switches |
| `config/vendors.json` | Vendor config. Add an `RLDatix` entry here |
| `config/settings.json` | Has a `Notify` block already added |
| `modules/Common.psm1` | `Invoke-HttpGetWithRetry`, `Get-JsonPaged`, `Import-Framework` |
| `modules/State.psm1` | `Compare-ReleaseState` hashes `Vendor\|Product\|Title\|PublishedDate\|SourceUrl` to detect NEW vs UNCHANGED |
| `modules/AdoWorkItem.psm1` | **Stub for ADO User Story POST.** The other agent owns it. Don't refactor. |
| `tasks/VendorMonitor/Collectors/ApiCollector.ps1` | Generic JSON-API collector. Won't work directly — XML feeds need a different parser |
| `tasks/VendorMonitor/Collectors/Overrides/Invoke-EcteonCollector.ps1` | Example of the `Invoke-OverrideCollector` dispatch contract (Ecteon is disabled in current `vendors.json`) |

### Recommended approach: a new override collector

Create `tasks/VendorMonitor/Collectors/Overrides/Invoke-RLDatixCollector.ps1`
that:
1. GETs the two XML feeds (no pagination needed — they're bounded).
2. Parses each with `[xml]` (PowerShell native XML).
3. Emits **one normalized record per release number** with summary
   statistics:
   - `Vendor` = `RLDatix`
   - `Product` = `RL6`
   - `Title` = `RL6 <Version>`
   - `PublishedDate` = *(unknown — S3 has no per-version dates)*
   - `SourceUrl` = the landing page URL from `.env`
   - `RawBody` = short summary text (enhancement count + fix count + module list)
   - `Id` = `rl6-<version>` (stable key for state diff)

The existing `Get-RecordKey` and `Compare-ReleaseState` will then
correctly classify each version as NEW the first time it appears and
UNCHANGED on subsequent runs.

### Why per-version instead of per-row?

Per-row entries (5 enhancements + 49 fixes for 6.34) would generate
54 NEW records per release and 54 work items. **Not** what the user
wants. One record per version = one work item per release, which is
the notification contract.

### State and diff

`Compare-ReleaseState` will see the new version record and tag it
NEW. The collector can additionally expose the underlying enhancement
and fix entries via the raw body / summary for the HTML rendering, but
they are not independent records.

## Quirks / Known Issues

1. **No `PublishedDate` for releases.** The S3 source has no
   per-version timestamp. The XML was last modified as a whole (you can
   fetch the S3 object metadata with a HEAD request to get the
   `Last-Modified` header). Workaround: use S3 object `Last-Modified`
   as the `PublishedDate`, or omit it.

2. **`RLRefNumber` can be empty.** One 6.34 fix entry has a blank
   `<RLRefNumber</RLRefNumber>`. Treat empty as "not provided".

3. **HTML inside `<Summary>`** is not always escaped (e.g.
   `&` may appear as raw `&`). When rendering, re-escape.

4. **Hotfixes share the same major.minor as a prior release.** Treat
   `6.33.1` as a separate record keyed `rl6-6.33.1` so the state diff
   doesn't suppress it as "same as 6.33".

5. **`vendor-state` branch already has an entry for this URL family.**
   The `state/SOURCES.md`, `state/latest-release.md`, and refreshed
   `state/vendor-state.json` from earlier this session are on the
   `vendor-state` branch (commit `d4a3668`). They tracked the Zendesk
   source. If you want to switch trackers to the S3 source, that work
   needs to be re-done on the S3 feed. The schema (`id:<key>` keyed
   by stable id) still applies.

6. **Other agent owns ADO work-item creation.** Don't touch
   `modules/AdoWorkItem.psm1` or the notifier block in `Run.ps1`.
   Co-ordinate via the shared branch.

7. **Earlier work in this session (Zendesk collector at
   `tasks/VendorMonitor/Collectors/Overrides/Invoke-RLDatixCollector.ps1`)
   points at the WRONG source.** It currently hits
   `rldatix-public.zendesk.com`. **Rewrite it to use the S3 XML
   feeds** per the spec above, or replace it with a new collector.
